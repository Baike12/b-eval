# 02 · 能力维度与任务体系

## 2.1 能力分类模型

平台采用**双轴分类**：能力维度轴回答「Agent 缺哪种能力」，场景域轴回答「Agent 在哪类真实场景里不行」。两个轴独立标注，任一任务可同时落在多个能力维度和多个场景域上。

### 2.1.1 能力维度轴（一级）

依据 Agent 评测综述的四条基础能力主线（规划 / 工具使用 / 自我反思 / 记忆）与 AgentBoard 的六维加权分合并而成，划为 6 个一级维度：

| 维度 | 内涵 | 典型考察方式 |
|---|---|---|
| **C1 规划与推理** | 分解任务、选择路径、在约束下做决策 | 多步任务、部分完成度评分、步数效率 |
| **C2 工具与接口使用** | 正确调用工具、参数正确、组合多个工具、处理调用失败 | 工具调用匹配率、参数正确率、环境终态比对 |
| **C3 状态与记忆保持** | 跨轮/跨步跟踪状态、记住历史信息、化解冲突信息 | 进度率、记忆类数据集、增量多轮追问 |
| **C4 交互与协作** | 与用户/其他 Agent 对话、澄清需求、处理变更与打断 | 用户模拟器任务、多 Agent 协作任务 |
| **C5 错误处理与自我纠错** | 失败后定位原因、修正、重试而不发散 | 注入失败分支的任务、失败后恢复率 |
| **C6 鲁棒性与安全** | 抵抗提示注入、越权操作、不当内容、识别不可完成任务 | 攻防任务集、infeasible 任务 |

### 2.1.2 能力维度轴（二级，共 18 项）

| 一级 | 二级标签 |
|---|---|
| C1 规划与推理 | 任务分解、约束遵循、路径选择、长程规划、目标澄清 |
| C2 工具与接口使用 | 工具选择、参数构造、工具组合、工具失败恢复、协议适配（含 MCP） |
| C3 状态与记忆保持 | 工作记忆、会话状态跟踪、长期记忆、信息冲突化解、上下文压缩 |
| C4 交互与协作 | 需求澄清、信息主动同步、用户意图变更响应、多 Agent 协作 |
| C5 错误处理与自我纠错 | 失败定位、自我修正、重试策略、幻觉抑制 |
| C6 鲁棒性与安全 | 提示注入抵抗、越权拒绝、不可完成任务识别、内容合规 |

**标注规则：**
- 每个任务**至少 1 个**一级维度标签，**建议 2 个**；超过 3 个视为标注过宽，需复核。
- 二级标签必须命中该任务的实际失败点，不按「这类任务通常考什么」推断。
- 标签是**可多选**的，且**互斥检查**在任务入库前自动执行（同一二级不可重复）。

### 2.1.3 场景域轴

按「Agent 操作的对象是什么」划分，与 τ²-bench 的域打包思路一致：

| 域 | 覆盖内容 | 参考来源 |
|---|---|---|
| **D1 网页与浏览器** | 信息检索、表单填写、跨站点操作、可见性敏感的网页任务 | WebArena、VisualWebArena、ClawBench |
| **D2 桌面与 GUI 应用** | 操作系统、办公软件、图像/媒体、IDE | OSWorld、WindowsAgentArena |
| **D3 代码与软件工程** | 仓库级修 bug、实现功能、终端运维、训练与调参 | SWE-bench、terminal-bench、MLE-bench |
| **D4 工具与 API** | 函数调用、REST/服务集成、MCP 服务、企业系统 | BFCL、MCPMark、τ-bench |
| **D5 真实业务流程** | 客服、电商、旅行、政务等端到端业务流程 | τ²-bench、VitaBench |
| **D6 多 Agent 协作** | 分工、交接、协同交付 | TheAgentCompany、AgentVerse |

**跨域任务：** 允许一个任务横跨多个域（如「在网页上比价 → 在办公软件出报表」），用于考察 C1/C4。

### 2.1.4 能力分合成规则

平台**不产出单一「能力总分」**，但提供可配置的加权视图。权重必须显式声明并随结果落盘，规则：

- 权重以「维度 → 域」两级给出，每级权重之和归一化为 1。
- **缺失覆盖时不静默补零**：某个维度下没有任务被评测时，该维度得分标记为「无覆盖」，不参与加权，并在报告中标红。
- 加权分只用于内部回归对比，**对外榜单必须同时展示未加权的分域原始分**。

## 2.2 任务单元与元数据

一个任务的完整定义包含以下字段。字段名仅为功能性命名，具体存储格式见【待技术方案】。

| 字段组 | 内容 | 必填 |
|---|---|---|
| **身份** | 任务 ID（稳定、全局唯一、不复用）、显示名、所属基准、所属任务集版本 | ✔ |
| **能力标注** | 一级维度列表、二级标签列表、难度等级、场景域列表 | ✔ |
| **任务描述** | 面向 Agent 的自然语言指令；面向 Agent 之外的评测者说明（可选） | ✔ |
| **初始状态** | 环境快照标识、初始数据、初始文件、初始凭据、随机种子 | ✔ |
| **交互契约** | 动作空间描述、观测形态、终止条件、预算上限、是否允许多轮 | ✔ |
| **判定条件** | 判分器列表、组合方式、部分给分规则、目标状态或参考解 | ✔ |
| **参照材料** | 参考解（可选）、参考轨迹（可选）、领域策略文档（可选） | ✖ |
| **元信息** | 作者、来源、难度标注依据、预估人类耗时、预估 Agent 耗时、创建时间、最后修订时间、废弃状态 | ✔ |

**设计要点：**

- **任务 ID 不可变、不可复用。** 废弃的任务保留在库中并标记废弃状态，ID 永不再分配给新任务——否则历史分数会指向不同的题。
- **难度是必填字段**，来源为人工标注 + 预估耗时 + 实际失败率三者的综合，判定规则见 2.5。
- **「面向 Agent 的指令」与「面向评测者的说明」严格分离。** 前者参与运行，后者只在报告与评审界面出现，避免泄题。
- **判定条件与任务描述分离存放。** 判定条件不允许出现在 Agent 可访问的环境内（判分不可见，见 06 章）。

## 2.3 任务模板化与参数化

参考 WebArena 的做法（190 个意图模板 → 812 个任务实例），平台支持任务模板化：

- **模板**定义任务骨架：指令模板、动作空间、判定方式、难度。
- **参数实例**填充具体取值，生成多个任务实例。
- **实例必须各自独立计分**，且实例 ID 各自稳定。
- **模板实例化后的分布必须显式声明**：如果一个模板产出 20 个实例，这 20 个实例在整体分母中占 20 份权重——需在报告中标出模板组，防止靠「多实例模板」放大某类任务的分母占比。
- 模板实例化的**参数域需做去重与覆盖检查**，避免生成语义重复的实例（参考 τ²-bench 按 `write_profile` / `issue_persona` 分层抽样的做法：分层 → 定种子 → 冻结 → 生成 digest）。

## 2.4 任务集划分

一个基准下同时存在多个任务集，各自独立版本化：

| 任务集 | 可见性 | 用途 | 约束 |
|---|---|---|---|
| **样例集（smoke）** | 公开 | 接入自检、CI 冒烟 | 每域 ≤ 10 题，耗时 < 10 分钟 |
| **开发集（dev）** | 公开 | 任务作者调试判分器、任务试跑 | 可反复调用，不计入任何榜单 |
| **公开测试集（test-public）** | 公开 | 常规对外评测 | 公开后不再修改 |
| **私有测试集（test-private）** | 不公开 | 官方榜单、可信评测 | 判分细节与部分题目内容不可见 |
| **压力集（stress）** | 公开 | 长上下文、超长程、鲁棒性专项 | 单独出分，不并入总分 |

**规则：**
- **dev / test 的任务 ID 不重叠**。任务作者在任务入库时必须声明所属划分；平台自动校验同一任务 ID 不同时出现在两个划分中。
- **公开测试集一经发布即冻结**。修复题目缺陷只能通过发布新版本任务集完成，旧版本分数保留且标注版本号。
- **私有测试集的存在意味着分数不可跨平台比较**，因此报告必须在显著位置标注「本分数来自私有任务集」。
- **压力集不并入总分**——它的难度分布与常规集不同，混入会破坏可比性。

## 2.5 难度分层

难度采用**四档**，定义如下（每档给出可操作判定，不使用主观形容）：

| 档位 | 判定依据（满足任一即归入该档，取最高档为准） |
|---|---|
| **L1 简单** | 单步或双步完成；无外部依赖；Agent 不需要读取额外信息即可作答 |
| **L2 中等** | 3–8 步；需要 1 个以上工具；存在单一正确路径；失败原因唯一 |
| **L3 困难** | 8–20 步；需要组合多个工具或跨应用；存在多条可行路径；需要读取非显式指定的资料 |
| **L4 极难** | > 20 步或需要长程记忆；参考解本身较复杂；任务对真实人类有明确耗时门槛（预估人类耗时 > 20 分钟） |

**难度标签的自动校验（防止标注漂移）：**
- 任务集发布前，用基线 Agent 跑一遍，得到实际成功率。
- **标注与实测冲突告警**：标 L1 但基线成功率 > 90% → 降级告警；标 L4 但基线成功率 > 70% → 升级告警。
- 每半年重跑一次基线校准，产出难度校准报告。

## 2.6 环境与状态隔离

每个任务运行在**独立的环境实例**上，实例之间不共享可变状态。

**任务生命周期四阶段**（参考 MCPMark 的 Setup→Execute→Verify→Cleanup）：

| 阶段 | 内容 | 失败处理 |
|---|---|---|
| **准备** | 拉起环境实例、加载初始数据与快照、校验环境健康 | 失败 → 记为平台故障，不计入分母 |
| **执行** | Agent 与环境交互直至终止 | Agent 崩溃 → 记为模型失败，计入分母 |
| **判定** | 执行判分器、采集判定证据 | 判分器异常 → 记为判定故障，单独统计 |
| **清理** | 销毁环境实例、回收凭据与临时数据 | 清理失败 → 告警，人工介入 |

**隔离要求：**
- 每个 Trial 使用独立的环境实例与独立凭据，禁止跨 Trial 复用有状态资源。
- 判分所需的最终状态快照在「判定」阶段产生，判分过程只读快照，**不在 Agent 的环境上直接执行**。
- 对可回滚的环境（虚拟机/容器快照），支持「回滚到初始快照后重跑判分」。

## 2.7 任务来源与生产流程

任务来源分三类，各有独立准入标准：

| 来源 | 准入要求 | 附加约束 |
|---|---|---|
| **外部基准导入** | 原基准的数据与判分语义需完整映射到平台模型 | 导入后**必须重跑一次基线**并生成对照分；原基准分数与平台分数并列展示 |
| **内部构造** | 走完整的新题校验流程（见 2.8） | 判分代码对被测方不可见 |
| **社区提交** | 走完整的新题校验流程 + 人工评审 | 提交者署名；未通过评审不进入正式集 |

## 2.8 任务入库校验闸门

**任何新任务进入 dev 之前，必须全部通过；进入 test 之前必须额外通过 2–5。**

| # | 校验项 | 判定标准 | 依据 |
|---|---|---|---|
| 1 | **可解性** | 存在参考解且参考解跑通，判定为通过 | 参考 terminal-bench 的 oracle agent 自检 |
| 2 | **判分器可信度** | 参考解通过 + 若干「错误解」（故意做错）全部不通过 | 参考 SWE-bench 的 fail-to-pass / pass-to-pass 双集 |
| 3 | **判分器非平凡** | 至少一个判分器不是恒真；空操作不得通过 | 参考 SWE-bench 对「测试没真的跑过」的证据校验 |
| 4 | **平台故障分离** | 人为制造的环境故障被正确标记为「不计入分母」 | 参考 OSWorld `unscored_errors`、ClawBench `adjusted_eligible` |
| 5 | **难度可信度** | 实测成功率与标注难度不冲突（2.5 规则） | 参考 AgentBoard 难度分层统计 |
| 6 | **判分不可见** | 在 Agent 可访问范围内检索不到判分条件与判分逻辑 | 参考 TheAgentCompany 判分脚本加密 |
| 7 | **标注完整性** | 能力标签、域标签、预算、初始状态无缺项；标签互斥检查通过 | 平台内置检查 |
| 8 | **可复现** | 同种子重跑两次，判定结果一致（允许成本/时长浮动） | 平台内置检查 |

**校验不通过的任务不允许入库**，只能停留在草稿态。校验报告随任务保存，作为任务元数据的一部分。

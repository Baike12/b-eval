# 01 · 项目概述

## 1. 背景与问题

开源社区已有大量 Agent 基准（SWE-bench 6068 star、OSWorld 3229、τ²-bench 2284、AgentBench 3784 等），但把它们当作「可用的测评基础设施」时会撞到五堵墙：

**墙一：没有统一的被测对象接入方式。**
τ-bench 的 Agent 走「首轮 tool_call 后注入 tool 消息」的固定循环，VitaBench 走 `generate_next_message`，MCPMark 走 LiteLLM tool loop，AgentCompass 走 `run_task`。同���个 Agent 想跑两个基准，必须写两套适配层，且两边行为语义不等价，跨基准分数不可比。

**墙二：没有统一的判分抽象。**
OSWorld 用「结果获取器（43 种）× 判定函数（120 种）」两层解耦；MCPMark 用独立判分脚本按退出码判；TheAgentCompany 用可插拔 checkpoint 累加；AgentDojo 把任务拆成「效用」和「安全」两个正交轴；VitaBench 用 rubric 条目滑动窗口。判分器不可跨项目复用，评测平台能力无法沉淀。

**墙三：基础设施故障直接污染分数。**
τ-bench v1 把任何异常（含 API 报错）记 0 分并计入分母，导致 pass^k 被机房抖动拉低；OSWorld 用 `unscored_errors` 把「环境挂了」排除出分母；ClawBench 用 `adjusted_eligible` 做同样的事。三套口径互不兼容，且都没有被写进分数本身——看榜的人无从判断一个 0 分是模型不行还是网络断了。

**墙四：判分逻辑对被测方可见。**
多数基准的判分脚本就放在任务目录里，被测 Agent 有 shell 就能读到「什么条件算通过」。TheAgentCompany 用加密脚本规避了这一点，但只此一家。

**墙五：题目生产没有质检闭环。**
一个基准的题目成本极高（OSWorld 369 题、terminal-bench 241 题均为人工构造），但普遍缺「参考解能解出 / 判分器不会误判 / 难度标注可信」的前置校验，导致题目本身的缺陷长期潜伏。

## 1.2 项目定位

**b-eval 是一个通用的 Agent 测评平台，不是一个具体的 Agent 基准。**

它提供的是「把一套 Agent 放到一套可复现、可解释、可对比的任务上跑出分」的完整能力；具体测什么任务，由平台内的任务集决定。

与现有项目的分工：

| 关系 | 对象 | b-eval 的立场 |
|---|---|---|
| 复用 | SWE-bench / OSWorld / τ²-bench / AgentBench 等已有基准 | 作为「可接入的任务集」纳入，平台不重造题 |
| 替代 | 各基准自带的评测框架 | 提供统一的运行编排、判分、报告能力 |
| 补齐 | 人工 rubric、跨基准统一指标、判分可观测 | 现有项目普遍缺失的部分，由平台统一提供 |
| 延伸 | 私有任务集、内部 Agent 版本回归 | 平台必须支持非公开题目的全生命周期 |

## 1.3 目标

**G1 · 一套接入协议吃下所有 Agent。** 任意 Agent 只需实现一个最小接口即可被评测，评测行为与 Agent 内部实现解耦。判定标准：该 Agent 在不改平台的前提下接入成本 ≤ 1 天。

**G2 · 一套判分抽象吃下所有任务类型。** 确定性校验、环境终态比对、规则断言、脚本判分、LLM 判分、人工复核——六类判分器统一在同一模型下，跨任务、跨基准可组合。

**G3 · 分数可信且可解释。** 任何一次评测的分数都能回答三个问题：哪些题没分、为什么没分、这个「没分」是模型的问题还是平台的问题。

**G4 · 同题跨 Agent 可比。** 同一份任务、同一套预算口径下，不同 Agent 的分数直接可比，不受各自框架的默认值影响。

**G5 · 评测成本可预测。** 跑之前能估出这次评测的 token 量、费用、耗时上限；跑超了能立刻知道。

**G6 · 题目质量有前置闸门。** 新题进入正式任务集之前，必须通过可解性、判分可信度、难度可信度三项校验。

## 1.4 非目标

- **不做通用 Agent 框架**。b-eval 不提供 Agent 的规划、记忆、反思等运行时能力，只提供「被测对象接入」与「跑起来」。
- **不做模型训练/强化学习**。评测与训练是两件事。轨迹导出为可复用格式是本平台的边界内事项，但训练闭环不在范围内。
- **不追求题量**。宁可 200 题经得起检验，不要 2000 题混杂质量问题。
- **不做通用质量评测**。不与 DeepEval / Ragas / promptfoo 竞争「LLM 输出质量断言」市场；b-eval 只关心 Agent 行为。
- **不追求单分数**。不提供「一个数字代表 Agent 能力」的指标；平台强制至少按能力维度与场景域双轴分解输出。

## 1.5 用户角色

| 角色 | 典型诉求 | 核心使用场景 |
|---|---|---|
| **Agent 开发者** | 我的 Agent 在真实任务上表现如何？这次改动是变好还是变差？ | 提交评测、看报告、与上个版本对比、看失败轨迹定位问题 |
| **Agent 开发者 / 平台工程师** | 我要给别人一个能跑的 Agent，测评怎么接？ | 接入 Agent、跑通样例任务、查看接入自检结果 |
| **任务作者** | 我要新增一批考题 | 建任务、配判分器、跑校验、提交入集 |
| **基准维护者** | 这个基准的题目还成立吗？难度分层还准吗？ | 版本管理、任务集审计、题目修订与废弃 |
| **评测组织者** | 这批 Agent 谁更强？结论靠得住吗？ | 批量编排、跨基准对比、排行榜发布、结果审计 |
| **安全评审者** | 这个 Agent 会不会被提示注入带偏？ | 攻防任务集、ASR 报告、防御策略对比 |

## 1.6 核心概念模型

平台内只有七个一等概念，其余皆为它们的配置。

```
基准(Benchmark)
  └─ 任务集(TaskSet)  ── 版本化、冻结、可发布
       └─ 任务(Task)
            ├─ 场景域(Domain)          任务所属的环境/业务场景
            ├─ 能力标签(CapabilityTag) 任务考察的能力维度
            ├─ 难度(Difficulty)        任务的难度分层
            ├─ 初始状态(InitialState)  任务开始前的环境快照与数据
            ├─ 交互契约(Contract)      动作空间、观测形态、终止条件、预算
            └─ 判定条件(Judgement)     判分器集合与组合方式

被测对象(Agent) ── 接入适配器(AgentAdapter) ── 协议(AgentProtocol)

运行(Run) ── 运行计划(Plan) ── 试次(Trial) ── 轨迹(Trajectory)
                                    └─ 判定(Verdict) ── 指标(Metric)
```

**关键约束：**

- **任务与 Agent 完全解耦。** 任务不知道 Agent 存在，Agent 不知道任务是什么，只有「契约」是双方的唯一接口。
- **试次（Trial）是评测的原子单位。** 一个 Trial = 一次完整的「任务 × Agent × 随机种子 × 预算」执行。所有指标最终都由 Trial 聚合而来。
- **判定与执行分离。** 判定可以在不重跑 Agent 的情况下，对已保存的轨迹重新执行（离线重打分）。这是排障、换判分口径、第三方审计的基础能力。
- **一切分数都必须能下钻到 Trial。** 报告里的每个数字都能追到具体是哪几个 Trial 算出来的。

## 1.7 差异化定位

b-eval 相对现有工作，**唯一必须做到、且当前无人做到**的三件事：

1. **统一的 Agent 接入协议 + 跨基准统一指标。** 同一个 Agent 用同一套适配器跑 SWE-bench、OSWorld、τ²-bench，得到的分数在同一个坐标系里。
2. **判分不可见 + 判分可审计。** 判分逻辑对被测 Agent 不可见；同时对平台运营者完全可审计——每一次改分都有作者、理由、时间戳。
3. **分数可信度显式化。** 每个分数自带「这份分数有多可信」的信息：多少 Trial 因平台原因被排除、judge 一致性多高、置信区间多宽。

## 1.8 开放问题（需产品决策）

| 编号 | 问题 | 影响面 |
|---|---|---|
| Q1 | 平台是否对外运营排行榜？公开榜单需要考虑提交流程与防刷分，私有部署不需要 | 提交流程、结果可见性、审核队列 |
| Q2 | 判分代码不可见采用「加密下发」还是「判分在独立环境执行、被测方无读权限」？ | 任务包格式、沙箱拓扑 |
| Q3 | 是否允许第三方提交 Agent 成绩？若允许，判分逻辑必然对提交方可见，与 G-「判分不可见」冲突 | 排行榜设计与安全边界 |
| Q4 | 任务集是否强制分层（公开子集 / 半公开 / 私有）？私有集的存在会使分数无法横向比较 | 分数可比性、榜单设计 |
| Q5 | 用户模拟器（人设化用户）是一等公民还是可选组件？ | 任务模型、交互契约 |

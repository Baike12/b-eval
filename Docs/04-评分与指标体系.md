# 04 · 评分与指标体系

## 4.1 判分器分类

平台把判分逻辑抽象为六类判分器。任务通过「引用判分器 + 组合规则」声明判定条件，判分器实现与任务解耦，跨任务、跨基准可复用。

| 类别 | 编号 | 判定依据 | 典型实现 | 参考来源 |
|---|---|---|---|---|
| **状态校验** | J1 | 环境最终状态是否符合期望 | 读取环境快照中的指定字段并比对 | OSWorld 的 metric 层 |
| **结果获取** | J2 | 产物内容（文件、数据库行、页面状态）是否符合期望 | 拉取产物后套用比较规则 | OSWorld 的 getter 层 |
| **动作断言** | J3 | Agent 是否调用了必需的动作序列、参数是否正确 | 按动作名与参数逐条匹配 | τ²-bench 的 ACTION 判据 |
| **规则判据** | J4 | 声明式规则集（数值比较、正则、集合关系、结构化比对） | 规则声明 + 通用执行器 | OSWorld 的 `_match_value_to_rule`、terminal-bench 的测试解析 |
| **模型判分** | J5 | 用自然语言 rubric 条目判定轨迹质量 | rubric 条目 + 判分模型 | VitaBench、TheAgentCompany 的 LLM 判定 |
| **人工复核** | J6 | 人工对轨迹/产物给出结论 | 标注工作台 | AgentBoard 的专家复核、Chatbot Arena 的人类偏好 |

### 4.1.1 判分器统一契约

任何判分器必须返回统一的三态结果之一：

| 结果 | 含义 | 是否计入分母 |
|---|---|---|
| **通过（PASS）** | 判据满足 | ✔ |
| **未通过（FAIL）** | 判据不满足 | ✔ |
| **未计分（UNSCORED）** | 判分器自身故障、判分模型不可用、判据无法评估 | ✘，并计入「判定故障率」 |

**「未计分」是一等状态。** 判分模型超时不能等同于「判为不通过」——否则平台自身的稳定性问题会转化成 Agent 的能力扣分。参考 Inspect AI 的 `Score.unscored(reason="grader_failed")` 与 τ²-bench v2 把 infra error 剔出分母的做法。

### 4.1.2 关键设计：判定依据与判定方式解耦

参考 OSWorld 的二元解耦，把它提升为平台通则：

- **「取什么」与「怎么比」是分离的两个动作。** J2 负责把结果取出来（一个文件、一行数据库、一个页面状态），J4 负责按规则比（等于、包含、数值近似、结构化匹配）。组合起来即可覆盖绝大多数确定性判定。
- 任务声明的是**引用**（"取 X，比 Y"），不是实现。新增一种比较规则不需要改任何框架代码。

### 4.1.3 状态判定 vs 动作判定

平台明确区分两类判定，并在报告中分开呈现：

| | 状态判定（结果导向） | 动作判定（过程导向） |
|---|---|---|
| 问的问题 | Agent 达成了目标吗？ | Agent 走的路对吗？ |
| 允许多解 | ✔ 是 | ✘ 否（除非显式声明为「必需动作」） |
| 判定方式 | 环境终态 / 产物内容比对 | 动作序列与参数匹配 |
| 风险 | 可能误判（做了别的有用的事） | 可能过严（等价路径被判错） |

**默认只做状态判定。** 动作判定仅在任务显式声明时启用，且显式声明的动作序列被标注为「参考轨迹」，其语义是**可选的等价路径之一**，除非任务额外声明为「必需动作」（参考 τ²-bench 把 `actions` 从「必须走的路径」重新定义为「一条参考轨迹」的做法）。

### 4.1.4 「参考轨迹 ≠ 必需路径」的终态比对范式

这是平台推荐的默认判定方式，对多解任务尤其重要：

1. 构造一个**黄金环境**：干净初始状态 + 重放参考轨迹 → 得到目标终态。
2. 构造一个**被测环境**：干净初始状态 + 重放 Agent 的实际轨迹 → 得到实际终态。
3. 比对两个环境的最终状态。

好处：
- Agent 走任何等价路径都算通过（不惩罚不同的正确解法）。
- 不需要为每条任务手写判分脚本。
- 重放时**只执行「改变状态」的动作**，只读动作跳过——Agent 多查几次不影响终态比对；Agent 幻觉出的工具名被当作无操作跳过，与实况一致。

### 4.1.5 Rubric 条目化评分

针对无法用状态完全刻画的开放式任务（如「回复是否专业、是否覆盖了所有需求」），平台提供 rubric 机制：

- **rubric 条目化**：一条任务可声明多条 rubric，每条是一个可独立判定的原子要求。
- **每条 rubric 独立判定**：布尔结论 + 理由 + 支撑证据引用（哪一轮、哪次工具调用）。
- **状态可翻转**：一条 rubric 在后续轨迹中可能从「已满足」变为「被推翻」（如用户后来改主意，作废了之前的下单）。
- **滑动窗口**：当轨迹过长导致一次性评估不可靠时，用「窗口大小 W、重叠 O」的滚动窗口逐窗增量更新 rubric 状态；rubric 状态跨窗口保留。重叠的作用是防止「决定性信息恰好落在窗口边界」被漏判。
- **判分模型不可用时判为 UNSCORED，不判为 FAIL**（参考 VitaBench 与 τ²-bench 的 `unscored` 处理）。

**rubric 反作弊口径（内置于判分提示模板，不依赖任务作者自觉）：**
- 只看 Agent 的回复与工具调用；用户说了什么只作为引导，不作为完成证据。
- **查询类工具的返回值不算完成证据**——Agent 查到了不等于 Agent 完成了。
- **涉及状态改变的 rubric 必须确认该改变真的发生了**（如「必须真的下单」，用户说「我自己买」不算）。
- 判分理由必须引用具体轮次。

### 4.1.6 判分器组合与部分给分

- 多个判分器按**合取（全部满足）/ 析取（任一满足）**组合。
- **合取 + 部分给分**：每个判分器输出 0/1（或小数），总分 = 满足数 / 总数。此时任务不再是二值成败，而是连续分数。
- **判分器权重**：可声明权重，总分为加权平均；权重随任务保存并展示。
- **主判据（primary）**：每个任务必须指定至少一个主判据，用于二值成功率口径。其余为辅助判据，只贡献连续分。

**示例（任务「在零售系统里帮用户改订单」）：**

| 判分器 | 类型 | 作用 |
|---|---|---|
| 环境终态哈希比对 | J1 | 主判据：订单状态与黄金终态一致 |
| 必须说出的信息（订单号、改后金额） | J5（rubric） | 辅助：信息传达 |
| 必需动作（调用了改单工具） | J3 | 辅助：路径正确 |
| 未越权（未改动其他订单） | J1 | 辅助：范围约束 |

## 4.2 核心指标定义

所有指标的计算口径在此唯一定义，报告、榜单、导出格式一律引用本节。

### 4.2.1 记号

| 记号 | 含义 |
|---|---|
| `T` | 任务集的任务总数 |
| `t` | 单个任务 |
| `n_t` | 任务 t 的有效 Trial 数（已剔除平台故障） |
| `c_t` | 任务 t 中判定为通过的 Trial 数 |
| `k` | 重复次数（默认 1） |
| `S_t` | 任务 t 的成功判据结果集合（多判据时为「主判据通过」的布尔值） |
| `P_t` | 任务 t 的进度分（0–1，见 4.2.3） |

### 4.2.2 成功类指标

| 指标 | 公式 | 分母 | 含义 |
|---|---|---|---|
| **成功率 SR** | `Σ_t c_t / Σ_t n_t` | 有效 Trial 总数 | 任务级成功比例（k=1 时等同于 pass@1） |
| **pass@k** | `1 - Π_{i=0}^{k-1} (n_t - c_t - i) / (n_t - i)`（n_t < k 时该项记 NA） | 任务数 | k 次尝试中至少成功 1 次的概率（无偏估计） |
| **pass^k** | `C(c_t, k) / C(n_t, k)`（n_t < k 时该项记 NA） | 任务数 | k 次尝试全部成功的概率 |
| **avg@k** | `Σ_t (Σ_i reward_{t,i}) / Σ_t n_t` | 有效 Trial 总数 | 平均得分（对连续分任务尤为有用） |
| **任务通过率** | `|{t : c_t ≥ 1}| / T` | 任务数 | 至少成功过一次的题占比 |

**pass@k 与 pass^k 的取舍：**
- pass@k 回答「这题有没有可能做对」，反映能力上限。
- pass^k 回答「这题能不能稳定做对」，反映可靠性。
- **两者必须同时报告**，单报其一会误导（参考 τ²-bench 同时报告 pass^1..pass^k 的做法）。

**k < n_t 的处理：** 当部分任务的 Trial 数少于 k 时，该任务的 pass@k / pass^k 记为 NA（不参与该项平均），并报告**有效任务覆盖率**——避免「只跑通 1 次的题」被悄悄丢掉。

### 4.2.3 进度分（连续得分）

部分完成要给分，否则 Agent 在「完成 80%」和「完成 0%」之间会被等同对待。

进度分的定义由任务声明，平台提供三种标准形态：

| 形态 | 定义 | 适用 |
|---|---|---|
| **子目标达成率** | 已达成子目标数 / 子目标总数 | 有明确子目标的任务 |
| **环境进度** | 环境自身给出的进度信号（单调不减） | 环境原生支持进度反馈 |
| **判定加权得分** | 各判分器得分按权重加权 | 多判据任务 |

**硬性要求：**
- 进度分必须**单调不减**（同一 Trial 内不得回退），避免 Agent 通过倒退操作刷分。
- 进度分的上界与主判据一致：**主判据未通过的任务，最终分数仍由主判据封顶**（如主判据要求终态完全一致，则进度分只是辅助信息，不用于「部分得分」）。
- 报告需同时给出**二值成功率**与**连续平均分**两条曲线（参考 AgentBoard 的双轨做法）。

### 4.2.4 效率与成本指标

| 指标 | 定义 | 说明 |
|---|---|---|
| **成功任务平均步数** | 判定通过的任务的平均动作数 | 与同任务集基线对比 |
| **成功任务平均 token** | 同上，按 token 计 | |
| **成功任务平均费用** | 同上，按费用计 | 价格表随结果落盘 |
| **成功率-成本前沿** | 以成本为横轴、成功率为纵轴的多点曲线 | 参考「同时优化准确率与成本」的主张 |
| **无效动作率** | 未产生任何状态变化的动作数 / 总动作数 | 衡量发散程度 |
| **重复动作率** | 连续相同或等价动作占比 | 参考 WebArena 的重复动作早停规则 |
| **动作格式错误率** | 无法解析为合法动作的响应数 / 总响应数 | 衡量接入质量与 Agent 稳定性 |
| **grounding 准确率** | 合法且被环境接受的动作数 / 总动作数 | 参考 AgentBoard 的 grounding_acc |

**成本口径要求：** 费用按「模型输入 token + 输出 token + 判分模型消耗 + 用户模拟器消耗」全量计，**判分开销也要计入**——否则「多花 judge 成本换高分」的策略不可见。

### 4.2.5 失败归因指标

| 指标 | 定义 |
|---|---|
| **终止原因分布** | 各终止类型（完成 / 预算耗尽 / 协议违规 / 模型失败 / 平台故障 / 被取消）的占比 |
| **判定故障率** | 判定器返回 UNSCORED 的 Trial 占比 |
| **平台故障率** | 平台故障 Trial 占比（**不计入分母，但必须报告**） |
| **判分器级失败明细** | 各判分器的 PASS / FAIL / UNSCORED 占比，用于定位是哪个判据不靠谱 |

### 4.2.6 可靠性与置信区间

- **所有比例型指标必须附带置信区间**（默认 95%），区间计算方式可配置（二项正态、Wilson、自助重采样）。
- **重复运行的方差**：`std` 与 `stderr`，用于判断「A 比 B 高 1 个点」是否只是噪声。
- **judge 一致性**：多判分模型投票时，报告一致率与一致性系数（如 Krippendorff's alpha），低于阈值的任务集标记为「判分不可靠」。

## 4.3 分解与聚合口径

### 4.3.1 分解维度

同一份分数必须能沿以下维度分解：

| 维度 | 依据 |
|---|---|
| 场景域 | 任务的域标签（2.1.3） |
| 一级能力维度 | 任务的能力标签（2.1.1） |
| 二级能力标签 | 任务的二级标签（2.1.2） |
| 难度 | 任务的难度档位（2.5） |
| 任务集划分 | smoke / dev / test-public / test-private / stress |

**每个分解格子上报告：** 样本量、成功率、连续均分、置信区间。

### 4.3.2 聚合口径

两种聚合方式，**必须显式选择并在报告中标注**：

| 方式 | 定义 | 适用 |
|---|---|---|
| **按 Trial 加权（micro）** | 所有 Trial 等权 | 各任务重要度相同 |
| **按任务等权（macro）** | 先算每个任务的得分，再对任务取平均 | 避免「某任务 Trial 多」主导结果 |

**默认使用 macro（按任务等权）。** 理由：Trial 数由评测者配置决定，不应由它决定任务权重。报告需同时给出 micro 数值供对照。

**分组等权原则：** 当按多个维度做笛卡尔分解时，每个格子等权，避免任务多的格子主导总分（参考 τ²-bench 的 cell 等权聚合与 AgentCompass 的 `category_mean`）。

### 4.3.3 缺失覆盖处理

- **无覆盖的格子不参与加权**，标记为「无覆盖」，在报告中显式呈现（不静默填 0）。
- **被排除的 Trial（平台故障）不计入分母**，但其数量与原因必须展示。
- **NA 的 pass@k 项不参与该项平均**，并报告该项的有效任务覆盖率。

## 4.4 Judge（模型判分）的使用规范

模型判分本身是引入噪声的环节，平台对它的使用做如下规范：

| 规范 | 内容 |
|---|---|
| **判分模型独立于被测模型** | 默认禁止用被测模型给自己打分；确需如此须在报告中显著标注 |
| **判分模型可配置且被记录** | 判分模型标识、版本、判分温度、提示模板版本，全部随结果落盘 |
| **温度固定为 0** | 判分默认确定性设置；判分模型不支持时需在报告标注 |
| **抗注入** | 送入判分器的被测文本做分隔符包裹，并把分隔符本身在文本中转义，防止 Agent 在输出里伪造分隔符骗过判分器 |
| **判分输出必须可解析** | 采用固定格式抽取结论（如 `GRADE: C/I/P`）；只认最后一次结论，防止推理过程中改口导致解析歧义 |
| **部分给分** | 支持三档结论（通过 / 部分 / 不通过），部分映射为 0.5 |
| **判分失败 = UNSCORED** | 判分模型报错、超时、输出不可解析，一律 UNSCORED，不判 FAIL，不重试超过限定次数 |
| **判分质量需校准** | 判分模型上线前必须在人工标注集上评估一致率，低于阈值不得用于正式评测 |

## 4.5 人工复核

- **复核工作台**：展示轨迹、判分证据、rubric 条目、当前判定，支持「维持 / 改判 / 标记有争议」。
- **改判留痕**：每次改判记录改判人、时间、理由、原判定、新判定。判定历史不可删除，只能追加。
- **复核抽样规则**：
  - **强制复核**：所有 UNSCORED 的 Trial、全部边界样本（分数贴近阈值）、所有高价值任务的首次运行。
  - **随机复核**：按比例随机抽取，比例可配置。复核结果用于估计自动判分与人工判分的偏差，产出「自动判分偏差率」指标。
- **复核是判分器校准的输入**：复核样本进入人工标注集，用于 4.4 的 judge 校准。

## 4.6 指标计算示例（口径一致性检查）

设任务集 T = {t1, t2, t3}，k = 3：

| 任务 | n_t | c_t | 进度均分 |
|---|---:|---:|---:|
| t1 | 3 | 3 | 1.00 |
| t2 | 3 | 1 | 0.55 |
| t3 | 2（1 次平台故障被剔除） | 0 | 0.10 |

计算：

- **SR** = (3 + 1 + 0) / (3 + 3 + 2) = 4/8 = 0.500
- **pass@3**：t1 = 1，t2 = 1 − C(2,3)/C(3,3) = 1，t3 = NA（n_3 < 3）→ 有效任务覆盖率 2/3 → pass@3 = (1 + 1)/2 = 1.000
- **pass^3**：t1 = C(3,3)/C(3,3) = 1，t2 = C(1,3)/C(3,3) = 0，t3 = NA → pass^3 = (1 + 0)/2 = 0.500
- **avg@3** = (3×1.00 + 3×0.55 + 2×0.10) / 8 = (3.00 + 1.65 + 0.20)/8 = 4.85/8 = 0.606
- **macro 成功率** = (1.000 + 0.333 + 0.000)/3 = 0.444（与 micro 的 0.500 不同，必须同时给出）
- **平台故障率** = 1 / 9 = 11.1% → **超过 5% 阈值 → 本次报告标记为「可信度不足」**

这个示例说明：**macro 与 micro 会给出不同结论，平台故障率会直接否决报告可信度**。这两点必须在报告中同时呈现。

# 03 · 评测执行与编排

## 3.1 一次评测的完整流程

```
① 选定任务集与版本  →  ② 配置评测计划（Plan）  →  ③ 预估成本
        ↓
④ 准备环境（每 Trial 独立实例）  →  ⑤ 执行交互（Agent ↔ 环境/用户）
        ↓
⑥ 采集轨迹与用量  →  ⑦ 判定（可离线重跑）  →  ⑧ 聚合指标
        ↓
⑨ 生成报告与对比  →  ⑩ 归档 / 发布
```

**关键设计：步骤 ⑦ 与 ⑤ 之间是可断开的关系。** 轨迹一旦落盘，判定可以脱离执行独立重跑——换判分口径、换 judge 模型、补人工复核，都不需要重新调用 Agent。这是平台最重要的工程能力之一。

## 3.2 被测 Agent 接入协议

### 3.2.1 协议定义

一个 Agent 适配器必须实现以下四类能力：

| 能力 | 语义 | 说明 |
|---|---|---|
| **会话启动** | 接收任务契约与初始观测，开启一次会话 | 由适配器负责构造首轮输入（不同 Agent 的首轮形态差异极大） |
| **推进一步** | 接收最新观测，产出下一个动作 | 动作形态由契约规定，适配器负责在 Agent 的原生输出与契约动作之间映射 |
| **结束判定** | 平台询问是否可结束时，适配器返回「继续」或「结束 + 终止理由」 | 终止理由是错误归因的关键数据，必须由适配器如实上报 |
| **用量上报** | 随时上报当前累计的 token、调用次数、已用时长、已花费用 | 用于预算熔断与成本统计 |

**协议明确不做的事：**
- 不规定 Agent 内部如何规划、是否使用记忆、是否有反思循环——这些是被测能力，不是协议内容。
- 不要求 Agent 暴露内部思维链，只要求暴露「动作 + 观测 + 用量」。
- 不要求 Agent 用特定的模型调用方式。适配器可以是「直接调模型」「包一个 CLI 工具」「包一个 IDE Agent」「包一个 MCP 客户端」。

### 3.2.2 三类适配形态

| 形态 | 适用对象 | 平台需要做的事 |
|---|---|---|
| **原生动作适配** | Agent 本身支持函数调用 / 结构化动作 | 提供动作 schema，让 Agent 直接对接环境；动作空间由任务契约给出 |
| **文本动作适配** | Agent 只输出自然语言动作（如 `Action: X with Action Input: Y`） | 平台解析文本动作；解析失败计入「动作格式错误率」并按契约规则处理 |
| **黑盒 CLI 适配** | Agent 是现成工具（如一个终端里的编码 Agent） | 平台在受控环境里跑它的进程，采集它的终端交互与文件产出 |

### 3.2.3 接入自检

平台提供接入自检套件：任务作者与 Agent 开发者用同一套样例任务（每域 ≤ 10 题，见 2.4）验证接入是否正确。

自检输出：
- 每个样例任务的期望动作序列与实际动作序列的差异（仅在样例任务自带参考轨迹时提供）。
- 动作格式错误率、契约违规次数。
- 用量上报是否正确。
- **自检不通过时，评测功能应被禁用**——避免把接入 bug 记成模型能力差。

## 3.3 交互契约

每个任务声明自己期望的交互形态，平台据此驱动执行。

### 3.3.1 动作空间

- 任务声明**动作集合**，每个动作包含：名称、参数结构、语义说明、是否改变环境状态、失败时的行为。
- 动作分为四类：**读**（查询，不改状态）、**写**（改变状态）、**推理**（纯内部计算）、**终止**（如转人工、声明完成）。
- **「是否改变状态」是独立于四类之外的开关**，因为存在「语义上是写但实际不改状态」的动作（参考 τ²-bench 的 `mutates_state` 与 `ToolType` 分离）。这个开关决定判定阶段重放时哪些动作被执行。
- 终止动作**必须独占一轮**：一次响应里同时包含终止动作和其他动作，整包拒绝并计入协议违规（参考 τ²-bench 的终止工具独占规则）。

### 3.3.2 观测形态

任务声明 Agent 每步能看到什么：

| 形态 | 说明 |
|---|---|
| 结构化观测 | 工具返回值（JSON）、状态查询结果 |
| 文本观测 | 页面文本、终端输出、文件内容 |
| 视觉观测 | 截图、可访问性树及其组合 |
| 混合观测 | 文本 + 视觉同时给出 |

**观测裁剪能力**（避免长上下文淹没任务本身）：视口过滤、token 上限截断、元素筛选、按需展开。裁剪规则由任务声明，不由平台擅自决定——否则不同任务的观测预算不可比。

### 3.3.3 终止条件

任务声明终止条件，平台与适配器共同执行：

| 终止类型 | 触发方 | 语义 |
|---|---|---|
| 正常完成 | Agent | 主动声明任务完成 |
| 声明不可完成 | Agent | 声明任务不可完成（仅在任务允许时正确） |
| 步数/回合耗尽 | 平台 | 触及任务声明的步数上限 |
| 预算耗尽 | 平台 | 触及 token / 时长 / 成本上限 |
| 协议违规 | 平台 | 连续动作格式错误、终止动作未独占轮等 |
| 环境异常 | 平台 | 环境侧报错或不可用 |

**终止理由必须被记录**，它是错误归因的第一手依据。

### 3.3.4 用户模拟器（可选）

部分任务（如业务流程、需求澄清类）需要模拟用户参与。任务声明「是否有人工用户」及其人设。

- **用户人设来源**分离为三层且互不重叠：通用行为准则 / 任务内人设 / 运行期覆盖。
- **用户必须被告知的信息**由任务指定，默认为「用户意图 + 用户已知信息」，不含判分条件、不含工具列表、不含参考解。
- **用户的信息披露策略**：默认「按需逐步披露」，一次只给当前步骤需要的信息；任务可声明「首轮全说」。
- **用户可改变主意**：任务指令中支持条件分支（如「如果没有某选项，你会选另一个」）。
- **结束信号**：用户发出显式结束标记，而不是靠模型自行判断。
- **用户不得编造**任务未提供的信息；模拟器的越界行为（编造、泄题、拒答）会被记录并计入「模拟器噪声」指标。

## 3.4 预算与限额

平台对每个 Trial 施加多重预算，取先触及者终止：

| 预算项 | 定义来源 | 说明 |
|---|---|---|
| 步数上限 | 任务声明 | Agent 可执行的动作数 |
| 回合上限 | 任务声明 | 对话轮数 |
| Token 上限 | 任务或计划声明 | 输入 + 输出 token 总数；支持表达式形式（如按输入量比例计算） |
| 时长上限 | 任务或计划声明 | 墙钟时长 |
| 成本上限 | 计划声明 | 按模型价格表折算的费用 |
| 调用次数上限 | 计划声明 | 模型调用次数 |
| 错误次数上限 | 任务声明 | 连续工具/环境错误次数 |

**执行前预估（F-RUN-02）：** 计划提交时，平台基于任务规模与历史运行数据，给出本次评测的 **token 量区间、费用区间、时长区间**。预估基于历史同任务集的实测数据，样本不足时给出保守上界并标注「预估置信度低」。

**熔断行为：** 触及任一预算 → 终止 Trial，判定为「预算耗尽」，按任务声明的规则计入分母或排除（默认计入分母，因为预算耗尽反映的是 Agent 效率问题；任务可声明为排除项）。

## 3.5 并发与限流

| 控制项 | 语义 |
|---|---|
| **最大并发 Trial 数** | 同时运行的任务数上限 |
| **最大并发环境实例数** | 受环境资源约束时的独立上限 |
| **模型调用并发** | 分为静态上限与自适应两种；自适应模式下，服务端限流时自动降速、服务端健康时自动提速 |
| **单任务并发** | 单个任务内允许的并行子动作数 |

**限流与重试的职责分离：**
- **模型侧限流**（429、配额不足）→ 退避重试，重试计入预算的「调用次数」但不计入「有效步数」。
- **环境侧瞬时错误** → 同上重试。
- **模型侧逻辑错误**（格式错误、幻觉工具名）→ **不重试**，直接作为该步失败并把错误反馈给 Agent（这本身是被测能力）。

**熔断阈值：** 同一任务连续失败达阈值 → 该任务的剩余 Trial 暂缓并告警，避免在环境故障时烧掉整批预算。

## 3.6 失败分类

平台把「一次 Trial 没跑完」的原因分为六类，每类进入不同的统计口径：

| 类别 | 含义 | 是否计入分母 | 是否重跑 |
|---|---|---|---|
| **完成** | 正常跑完并判定 | ✔ | — |
| **模型失败** | Agent 崩溃、输出不可解析、幻觉工具、超时 | ✔ | 可重试（换种子） |
| **平台故障** | 环境起不来、判分器异常、平台自身错误 | ✘（排除，单列统计） | ✔ 自动重试 |
| **预算耗尽** | 触及限额 | ✔（默认） | ✘ |
| **协议违规** | 动作格式持续错误、契约被破坏 | ✔ | ✘ |
| **被取消** | 人工中止、评测组织者取消 | ✘ | 由发起方决定 |

**关键约束（F-RUN-06）：平台故障永远不计入分母，且必须在报告中单列「本次评测的平台故障率」。** 若平台故障率超过阈值（默认 5%），整份报告标记为「可信度不足」，不参与榜单。

## 3.7 断点续跑与幂等

**续跑单元 = (任务 ID, Trial 序号, 随机种子)。**

- 平台按此三元组记录已完成单元；重启后自动跳过已完成单元。
- **续跑时配置必须一致**：若任务集版本、Agent 版本、判分配置、预算任一项发生变化，平台拒绝续跑并提示「这是一次新的评测」。判定依据来自计划指纹。
- **已完成的判定可单独重跑**（不改轨迹），用于换判分口径；重跑结果记录为新版本判定，保留历史判定以供对比。

## 3.8 轨迹与可观测性记录

每次 Trial 记录以下内容：

| 类别 | 内容 |
|---|---|
| **任务上下文** | 任务 ID 与版本、初始状态标识、能力标签、预算 |
| **交互序列** | 每一步的动作、观测、耗时、是否成功 |
| **终止信息** | 终止类型、终止理由、实际步数 |
| **用量** | 输入/输出 token、模型调用次数、工具调用次数、费用、端到端时长 |
| **判定** | 各判分器结果、组合后结果、判定证据、判分耗时 |
| **错误** | 各步的错误信息与堆栈、环境异常 |
| **环境证据** | 环境快照、截图、日志、产出文件（按任务类型可选） |
| **计划指纹** | 任务集版本、Agent 标识与版本、判分配置、预算、平台版本 |

**轨迹是平台的核心资产：**
- 所有报告数字都能下钻到具体 Trial。
- 支持**离线重打分**：用新判分器对旧轨迹重新判定，不调用 Agent。
- 支持**轨迹对比**：两次运行的轨迹可做差异对照（动作增减、参数漂移、成本/时延/结果变化）。
- 支持**导出**：轨迹可导出为通用格式，供外部工具消费。

## 3.9 评测计划（Plan）

一次评测由一个计划描述，至少包含：

| 配置项 | 说明 |
|---|---|
| 任务集与版本 | 选定任务集，锁定版本 |
| 被测对象 | Agent 标识 + 版本 + 接入配置 |
| 运行配置 | 重复次数（Trial 数）、随机种子策略、预算覆盖 |
| 判分配置 | 判分器选择、judge 模型、部分给分策略 |
| 并发与限流 | 3.5 节各项 |
| 归属信息 | 谁发起、归属哪个项目/版本、是否用于发布 |

**计划指纹**由上述内容派生，用于续跑一致性校验、结果归档与榜单提交校验。

# 06 · 安全鲁棒性与质量保障

本章解决三个问题：**分数会不会被作弊刷高**、**题目本身可不可信**、**平台给出的分数可不可信**。

## 6.1 评测过程防作弊

被测 Agent 在评测中拥有一定权限（读文件、跑命令、发网络请求），必须假设它会尝试读取判分逻辑、修改判分环境、构造假阳性。

### 6.1.1 判分不可见

| 措施 | 要求 |
|---|---|
| **判分条件不在 Agent 可访问范围** | 判分条件、期望终态、参考解不得出现在 Agent 可读的环境、文件、提示中 |
| **判分器实现不可读** | 判分器代码对被测方不可见（参考 TheAgentCompany 的加密下发思路） |
| **入库前自动扫描** | 任务入库时，在 Agent 可访问范围内检索判分关键词、期望答案片段、参考解特征串，命中即阻断入库 |
| **注入检测** | 判分证据中发现来自被测输出的可疑内容（如伪造的测试报告、伪造的完成声明）时，判定为「判定不可信」并单列 |

**采用哪种不可见机制（加密下发 vs 独立判定环境）取决于 Q2**，但**效果要求相同**：被测方在评测过程中拿不到判分逻辑。

### 6.1.2 判定环境与执行环境分离

- 判分在**独立于 Agent 环境的判定环境**中执行，Agent 无法干扰。
- 判定所需的最终状态在执行阶段结束后被**冻结为快照**，判定只读快照。
- 判定环境的凭据与 Agent 环境分离。

### 6.1.3 防「假阳性」的具体规则

判定必须自证「真的做了」，而不只是「结果看起来对」：

| 规则 | 说明 | 参考 |
|---|---|---|
| **执行证据必须存在** | 判据为「测试通过」时，必须有「测试确实执行了」的证据（非零用例数、执行摘要）；空结果不算通过 | SWE-bench 的 SUITE_RAN 证据校验 |
| **退出码与日志交叉校验** | 若退出码非零但日志中没有任何失败记录，判为无效（防补丁自己打印成功） | SWE-bench 的 exit code 交叉校验 |
| **测试标记边界** | 测试输出必须落在规定的起止标记之间，否则整条判定无效 | SWE-bench 的 START/END_TEST_OUTPUT |
| **跳过不算通过** | 被跳过的测试不满足「失败转通过」的条件 | SWE-bench 的 SKIPPED 语义 |
| **声明完成不算完成** | Agent 声明「已完成」只是终止信号，完成与否由判分器判定 | 通用原则 |
| **查询结果不算完成** | Agent 查到了信息不等于把事情办了 | rubric 内置口径 |

### 6.1.4 防「假阴性」与防误伤

防作弊不能变成「把好 Agent 也判死」：

- **参考解必须通过**（入库闸门第 2 项），确保判分器不会误杀正确解。
- **判分器改动需回归**：任何判分器修改，必须在判分器回归集（包含已知通过/已知失败的样本）上重跑，通过后才可生效。
- **判分器版本与题目版本绑定**：报告展示判分器版本，历史分数不因判分器升级而改变。

### 6.1.5 防「环境侧作弊」

| 场景 | 规则 |
|---|---|
| Agent 直接改判分文件 | 判分文件在独立环境，且执行前后做完整性校验 |
| Agent 污染后续 Trial | 每 Trial 独立环境实例 + 独立凭据（见 02 章 2.6） |
| Agent 缓存了上次结果 | 每 Trial 环境实例全新创建，或回滚到初始快照 |
| Agent 留下了后门 | 判定环境快照只取与任务相关的状态，不采信全局环境 |

### 6.1.6 成本型作弊

Agent 可能通过「少做多答」降低失败率（如遇到难题直接声明不可完成）。

- 任务的「不可完成声明」仅在任务确实存在该分支时才算正确，否则记为失败。
- **对声明不可完成占比异常高的 Agent，报告给出显式提示**（如「该 Agent 有 X% 的任务声明为不可完成」）。
- 提供「不可完成任务子集」专门测量这一能力，与其他任务分开计分。

## 6.2 攻防安全评测

平台支持专门的攻防评测（对应能力维度 C6），采用**效用-安全双轴**范式（参考 AgentDojo）。

### 6.2.1 实验设计

一次攻防实验由四个要素构成：

| 要素 | 内容 |
|---|---|
| **用户任务** | Agent 本该完成的任务（正常任务） |
| **攻击任务** | 攻击者希望 Agent 做的、用户并未授权的事 |
| **注入向量** | 攻击内容被植入的位置（工具返回、网页内容、文件、邮件等） |
| **防御策略** | Agent 侧或平台侧的防护措施 |

### 6.2.2 攻击库与防御库

- **攻击库**：攻击以「攻击策略 × 注入向量」的组合定义，每个攻击声明它试图达成什么。
- **注入点自动发现**：用探针（canary）自动定位「模型实际能看到哪些注入位置」，避免人工标注遗漏（参考 AgentDojo 的 `get_injection_candidates` 做法）。
- **防御库**：防御作为可插拔组件接入评测链路，包含：内容过滤、工具白名单、注入检测、来源标记、指令重述等。**防御与攻击同规格：一次实验只变一个变量。**

### 6.2.3 双轴指标

| 指标 | 定义 | 说明 |
|---|---|---|
| **效用（Utility）** | 无攻击时，Agent 正常完成用户任务的比例 | 防御不能以牺牲效用为代价 |
| **受攻击效用** | 有攻击时，正常任务仍被完成的比例 | |
| **定向攻击成功率（ASR）** | 攻击目标被达成的比例 | 越低越好 |
| **非定向攻击成功率** | Agent 出现异常行为（拒绝服务、输出异常）的比例 | 区分「被带偏」与「被搞挂」 |
| **攻防权衡曲线** | 效用与 ASR 的二维对照 | 用于选点：既要效用高又要 ASR 低 |

**报告必须同时给出无攻击效用与 ASR。** 只报 ASR 会奖励「直接拒绝一切」的防御；只报效用会掩盖注入风险。

### 6.2.4 拒绝服务型攻击

单独一类：攻击目标是让 Agent 无法完成任务（如诱导其陷入循环、触发验证码）。这类攻击的判定是「安全 = 未被完全阻断」，与定向攻击相反，需要独立通道与独立指标。

## 6.3 题目质量保障

### 6.3.1 入库闸门

见 02 章 2.8 的八项校验。其中第 1–3 项（可解性、判分器可信度、判分器非平凡）是**硬门槛**，不通过不允许进入 dev。

### 6.3.2 持续审计

题目发布后仍需持续体检，平台提供：

| 审计项 | 判定 | 处置 |
|---|---|---|
| **通过率异常** | 某题被 ≥ 95% 的 Agent 通过 | 饱和告警 → 复核难度或设计 |
| **失败率异常高** | 某题被 ≥ 95% 的 Agent 失败，且失败模式集中在同一处 | 可疑告警 → 检查判分器与题目 |
| **判分器与参考解不一致** | 参考解重跑不再通过 | 立即降级该题，回滚到上一版本 |
| **非确定性** | 同种子重跑判定不一致 | 隔离该题，排查环境随机性 |
| **耗时异常** | 实际耗时远超预估 | 排查是否存在环境等待/超时陷阱 |
| **标注漂移** | 实测难度与标注难度冲突 | 触发难度重标（见 02 章 2.5） |

**审计结论进入任务的「健康度」字段**，在报告与榜单中可见——一道题的健康度为「可疑」时，其贡献的分数在报告中会被标记。

### 6.3.3 题目修订纪律

- 任务内容修订**必须升版本**，旧版本保留。
- 修订需说明修订原因（修正判分器错误 / 修正歧义 / 修正事实错误 / 修正标注错误）与影响范围。
- **已发布版本的分数不因修订而重算**，除非修订被判定为「原题有误」，此时需同时发布原题分数的作废声明。

## 6.4 判分质量保障

### 6.4.1 Judge 校准

模型判分必须先校准后使用：

| 校准项 | 方法 |
|---|---|
| **人工标注集** | 维护一批人工判定的样本（含正例、反例、边界例） |
| **一致率评估** | judge 模型在标注集上的判定与人工判定的一致率 |
| **一致性系数** | 多个 judge 之间的 Krippendorff's alpha |
| **偏差分析** | 分析 judge 的系统性偏差（倾向给通过 / 倾向给部分分 / 对长轨迹更宽松） |
| **上线门槛** | 一致率与一致性系数低于阈值 → 不得用于正式评测；高于阈值 → 标注「已校准，judge=版本X」 |

### 6.4.2 Judge 失效保护

- 判分模型不可用 → UNSCORED，不判 FAIL。
- 判分输出不可解析 → UNSCORED，记录解析失败样本。
- 判定故障率超阈值 → 该次评测的报告标记「判分不可靠」。
- **判分开销计入总成本**（见 04 章 4.2.4）。

### 6.4.3 人工与自动判分的融合

平台支持三种融合模式，任务可选择：

| 模式 | 机制 | 适用 |
|---|---|---|
| **自动优先 + 人工抽检** | 自动判定，人工按比例抽检，产出偏差率 | 判据明确、量大 |
| **人工优先 + 自动复核** | 人工判定，自动仅做交叉校验 | 高价值、少量 |
| **双轨并行** | 自动与人工都判，差异超阈值时进人工仲裁 | 争议大、rubric 主观性强 |

**冲突处理：** 双轨不一致的样本进入仲裁队列；仲裁结论作为该样本的最终判定，并记录两种判定的原始值。

## 6.5 数据污染与时效性

| 措施 | 说明 |
|---|---|
| **时间戳化任务** | 任务带有「创建时间」与「最后校验时间」；超过有效期未复校的任务集标记「时效性存疑」 |
| **污染探针** | 把任务指令与期望答案的片段与公开语料比对，命中则标记「疑似污染」 |
| **私有集对冲** | 正式榜单同时包含公开集与私有集成绩，私有集分数抗污染 |
| **定期轮换** | 私有集定期更换题目；公开集每年至少一次实质更新 |
| ** Canary 标记** | 任务集附带可识别的标记串，用于检测任务内容是否出现在他处（参考 terminal-bench 的 canary 做法） |
| **时效性指标** | 报告给出「本次评测的任务集距上次实质更新的时间」，供解读分数时参考 |

## 6.6 平台自身的可靠性

分数可信的前提是平台本身可信。平台必须暴露自己的健康度：

| 指标 | 定义 | 阈值行为 |
|---|---|---|
| **平台故障率** | 平台/环境/判分器故障的 Trial 占比 | > 5% → 报告标记「可信度不足」，不参与榜单 |
| **判定故障率** | 判分器返回 UNSCORED 的占比 | > 3% → 报告标记「判分不可靠」 |
| **续跑一致性** | 同计划断点续跑后，结果与一次跑完的结果一致的比例 | < 99% → 排查幂等性 |
| **基准回归通过率** | 平台自带的基准回归套件通过率 | < 100% → 阻断发布 |
| **判分器回归通过率** | 判分器改动后的回归集通过率 | < 100% → 阻断判分器发布 |

**平台自带的基准回归套件**包含：最小任务集（每域 ≤ 10 题）、判分器回归集、指标计算的已知答案用例（如 04 章 4.6 的示例作为固定断言）。平台每次自身升级都必须跑通该套件。

## 6.7 敏感操作管控

评测环境可能涉及真实外部系统（真实网站、真实 API）。平台必须：

| 管控 | 要求 |
|---|---|
| **请求拦截** | 对外请求在离开受控环境前被拦截；平台只放行白名单目标 |
| **不可逆动作** | 下单、发信、支付、删除等动作，默认走拦截；任务显式声明允许才放行 |
| **凭据管理** | 使用一次性凭据，随 Trial 生成、随 Trial 销毁 |
| **频率约束** | 对外部系统设置请求频率上限，避免评测行为影响真实业务 |
| **数据最小化** | 受控环境内不放置真实用户数据；使用合成数据 |
| **外部影响记录** | 所有放行的对外动作被记录，可供事后审计 |
